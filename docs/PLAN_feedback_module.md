# 用户反馈模块（Feedback）设计方案 — 待评审

> 状态：**设计稿，待评审后实施**。对应 `Plan.md`「降级与观察项」中的登记项，三轴打分 I1·B1·C2 = 4。
> 提出背景：用户希望新增反馈模块，收集用户反馈与建议。
> 本方案的核心主张：**反馈的价值不在「收集」，而在「分诊」与「现场快照」——没有消费端与上下文，反馈箱就是只写不读的黑洞。**

---

## 一、问题与目标

### 1.1 问题

1. **改进依据靠猜测**：`Plan.md` 的 R7 / R8 / R9 等条目缺少真实用户输入，优先级裁决依赖推断而非证据。
2. **缺陷定位靠用户描述**：用户遇到报错时，能提供的信息通常只有「刚才那个功能不好用」。缺端点、缺页面、缺错误类型，复现成本高。
3. **反馈无处安放**：目前没有站内通道，用户只能通过外部渠道（邮件/私聊）反馈，散落且不可检索。

### 1.2 目标

1. **采集**：在错误现场与结果不满意现场提供一键反馈入口，提交成本控制在 10 秒内。
2. **定位**：自动附加**现场快照**（端点、页面、最近一次 LLM 调用失败类型、关联岗位/匹配记录），使一条反馈无需追问即可行动。
3. **闭环**：状态机 `open → triaged → planned → resolved / wontfix`，`planned` 可回填 `Plan.md` 条目号，形成「反馈 → 路线图」的可追溯链路。
4. **回执**：提交者可在站内看到自己反馈的状态，避免「提交后石沉大海」。

### 1.3 非目标（Out of scope）

- 不做工单系统（不承诺响应时效、不做 SLA、不做多轮客服对话）。
- 不做自动 AI 分诊（M1/M2 不做；M3 仅做关键词规则定级，不上模型）。
- 不做附件与截图上传（存储与合规成本高于收益，M3 再评估）。
- 不把主通道放在外部 Issue 系统上（需用户额外注册账号，转化率低，且暴露内部仓库）；仅可选地作为 M3 的导出手段。

## 二、核心设计决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 形态 | **独立资源** `feedback` 表，照 `cover_letters` / `experiences` 的解耦先例 | 反馈是流水数据，用户是实体数据；混入 `users` 表将无法查询与统计 |
| 核心字段 | **现场快照优先**，而非评分 | 只有输入框 + 五星评分得到的是「不好用」这类无法行动的输入；端点与错误类型才是可行动的 |
| 快照来源 | 前端传上下文（白名单校验）+ **服务端回填 `last_error`** | 前者是用户视角的定位，后者用户不可伪造，避免描述失真 |
| 分诊端 | 依赖 R3 管理员后台；M1 期间以数据库直查过渡 | 无 `/api/admin/*` 与后台页面，是当前唯一硬约束（见第七节风险） |
| 计费 | **不计费**，但限流 | 收积分会直接抑制反馈意愿；限流防止被当作免费存储滥用 |
| 台账 | **不写入 `llm_usage`** | 反馈提交不触发 LLM 调用，写入会污染用量与成本统计 |
| 用户可见状态 | 对外三态映射，内部五态 | `wontfix` 等内部语义直接暴露会引发无谓争议；对外统一为「已收到 / 处理中 / 已关闭」 |
| 隐私 | 不存 IP 明文；不自动附带简历/JD 正文；删除与导出并入 R6 | 反馈正文可能被用户粘贴简历片段，敏感度等同于简历本身 |

## 三、数据模型（拟）

### 3.1 `feedback`（新建）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | String(32) PK | uuid4 hex，与现有表一致 |
| `user_id` | String(32) index | 归属用户（必须登录，不接受匿名） |
| `category` | String(24) | `bug` / `feature` / `experience` / `other` |
| `severity` | String(16) | `low` / `medium` / `high`（用户自评，默认 `medium`） |
| `content` | Text | 正文，1–2000 字符 |
| `contact` | String(128) | 可选，用户主动留的联系方式（默认空，不强制索取） |
| `endpoint` | String(64) | 触发反馈的功能端点标识，**白名单校验**（见 5.1） |
| `route` | String(128) | 提交时所在页面路径，如 `/app/dashboard/match` |
| `last_error` | String(96) | 服务端回填：提交前 10 分钟内该用户最近一次失败的 `endpoint + error_type`，无则空 |
| `job_id` | String(32) nullable | 关联岗位卡（由页面上下文注入） |
| `derived_resume_id` | String(32) nullable | 关联匹配结果（由页面上下文注入） |
| `user_agent` | String(255) | 客户端 UA，用于区分浏览器/版本类问题 |
| `status` | String(16) | `open` / `triaged` / `planned` / `resolved` / `wontfix` |
| `admin_note` | Text | 分诊备注（对提交者可见的说明写在此字段） |
| `plan_ref` | String(64) | 落地的 `Plan.md` 条目号（如 `R5`），支撑「一键转条目」 |
| `resolved_at` | DateTime nullable | 关闭时间 |
| `created_at` / `updated_at` | DateTime | |

索引：`(user_id, created_at)`、`(status, created_at)`、`(category, created_at)`。

### 3.2 删除语义

- 用户可删除自己的单条反馈（`DELETE /api/feedback/{id}`）。
- 全量删除并入 R6 的 `/api/me/delete`（注销即删除）。
- 不做软删除：标记 `wontfix` 与「删除」语义不同，后者是用户的隐私诉求，必须真删。

## 四、接口契约（拟）

沿用现有约定：前缀 `/api`，JSON 字段 camelCase，DB 字段 snake_case。

### 4.1 M1 —— 采集与回执（无依赖，可独立交付）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/feedback` | 提交反馈。**限流 + 去重**；返回 `{ id, status, createdAt }`；上下文由服务端回填 |
| `GET` | `/api/feedback` | 本人反馈列表（分页，按时间倒序，返回对外三态） |
| `GET` | `/api/feedback/{id}` | 本人单条详情（含 `adminNote`）；非本人 404（不泄露存在性） |
| `DELETE` | `/api/feedback/{id}` | 本人删除单条 |

请求体示例：

```jsonc
// POST /api/feedback
{
  "category": "bug",
  "severity": "high",
  "content": "点「开始匹配」后一直转圈，最后提示 503",
  "contact": "",                          // 可选
  "endpoint": "match",                    // 白名单
  "route": "/app/dashboard/match",
  "jobId": "a1b2c3...",                   // 可选，页面上下文注入
  "derivedResumeId": null                 // 可选
}
```

响应不返回 `userAgent` / `jobId` 等内部元数据的完整值，用户在列表页只需看到正文、状态与时间。

### 4.2 M2 —— 分诊端（依赖 R3）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/admin/feedback` | 分诊列表：按 `status` / `category` / `severity` / 时间过滤，支持关键词搜索 |
| `PATCH` | `/api/admin/feedback/{id}` | 修改 `status`、写 `admin_note`、填 `plan_ref` |
| `GET` | `/api/admin/feedback/stats` | 按 `category` / `endpoint` / 周次聚合，供汇总使用 |

鉴权沿用 R3 的依赖注入强校验（`role=admin`），普通用户 403。

### 4.3 M3 —— 汇总与规则定级（可选）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/admin/feedback/summary?window=7d` | 周期性汇总：新增数、分类分布、Top 端点 |
| — | 关键词规则 | 正文含「崩溃 / 报错 / 打不开 / 白屏」时自动将 `severity` 提升为 `high`（纯规则，不上模型） |

### 4.4 对外状态映射

| 内部状态 | 对外展示 |
| --- | --- |
| `open`、`triaged` | 已收到 |
| `planned` | 处理中 |
| `resolved`、`wontfix` | 已关闭（`wontfix` 时在 `admin_note` 给出说明） |

## 五、现场快照策略

这是本模块与「普通意见箱」的核心分野。

### 5.1 前端提交（用户视角，白名单校验）

`endpoint` 仅接受以下枚举，服务端非白名单值一律 422：

```
match · cover_letter · ai_polish · ai_grammar · resume_import
export · jobs · resumes · templates · account · other
```

`route` 与 `jobId` / `derivedResumeId` 由所在页面上下文注入，**不让用户手填**——手填必然填错或留空。

### 5.2 服务端回填（用户不可控）

| 字段 | 来源 |
| --- | --- |
| `user_id` | 鉴权上下文 |
| `last_error` | 查询 `llm_usage` 中该用户最近 10 分钟内 `status=error` 的记录，取 `endpoint + error_type`（R1 已就绪，直接复用） |
| `user_agent` | 请求头 |
| `created_at` | 服务端时间 |

### 5.3 明确不做

- **不自动附带简历正文、JD 正文或最近一次匹配结果**。用户主动粘贴属其自主行为，系统不得越权采集。
- **不把 IP 写入数据库**。IP 仅在内存限流结构中使用（与 `export.py` 现状一致）。
- **不写 `llm_usage`**。反馈提交不产生 LLM 调用。

## 六、反滥用、限流与隐私

| 项 | 方案 |
| --- | --- |
| 限流 | 每用户每小时 10 条（`FEEDBACK_RATE_LIMIT_PER_HOUR`），复用 `app/api/export.py` 的滑动窗口实现；R6 抽象为公共限流模块后统一切换 |
| 超限响应 | 429 + `Retry-After`，文案与现有 AI 限流保持一致 |
| 去重 | `(user_id, endpoint, sha256(content)[:16])` 在 10 分钟窗口内重复 → 409 并提示「已收到相同反馈」 |
| 长度约束 | 正文 1–2000 字符，`contact` ≤ 128，超限 422 |
| 匿名化 | 不存 IP 明文；不在日志中输出正文 |
| 删除 | 单条删除 + 并入 R6 的 `/api/me/delete` |
| 导出 | 并入 R6 的 `/api/me/export`（反馈属个人数据） |
| 通知 | **后端无 SMTP/邮件基础设施**，M1 不实现任何通知；M2 的通知能力待接入邮件配置后单独立项。站内列表即为回执通道 |

## 七、分期与验收

| 阶段 | 范围 | 验收标准 |
| --- | --- | --- |
| **M1（薄切片，建议先行）** | `feedback` 表 + `POST/GET/DELETE /api/feedback` + 限流去重 + 账号菜单入口 + 「我的反馈」列表 | ① 提交后立即在列表中可见；② 超限返回 429 且带 `Retry-After`；③ 10 分钟内重复内容被拒（409）；④ 快照字段正确回填（含 `last_error` 命中场景）；⑤ **不产生 `llm_usage` 记录**；⑥ 非本人访问返回 404 |
| **M2（随 R3）** | 管理员分诊列表 + 状态流转 + `plan_ref` 回填 + 对外三态映射 | ① 管理员可改状态并写备注；② 用户侧状态随之更新且不暴露内部状态名；③ 标记 `planned` 时可写入 `plan_ref` 指向 `Plan.md` 条目 |
| **M3（可选）** | 汇总报表 + 关键词规则定级 + 导出为 Issue 文本 | ① 可产出 7 日汇总（新增数、分类分布、Top 端点）；② 含崩溃类关键词的反馈自动为 `high` |

**M1 的取舍说明**：M1 不包含分诊界面，因此存在「反馈被收集但暂未消费」的过渡期。这是刻意选择——采集能力的上线成本极低，而反馈的**时间价值**最高（用户当时遇到的问题，一周后往往已忘记细节）。过渡期以数据库直查承担消费端职责。

## 八、依赖与风险

### 8.1 前置依赖

| 依赖 | 原因 | 状态 |
| --- | --- | --- |
| R1 LLM 用量台账 | 提供 `last_error` 现场快照的数据源 | ✅ 已就绪 |
| R3 管理员运营后台 | M2 分诊端的前置；无后台则反馈无处消费 | ❌ 未开始（**关键路径**） |
| R6 备份与安全基线 | 限流模块抽象（复用而非复制）+ 个人数据导出/删除通道 | ❌ 未开始 |
| R2 AI 限流与计费 | 无强依赖；但限流实现建议与 R2 共用同一公共模块 | ❌ 未开始 |

### 8.2 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| **黑洞风险（最大）**：只写不读 | M1 过渡期以数据库直查承担；M2 必须随 R3 落地，否则模块关闭降级为「收集但暂不承诺处理」 |
| 冷启动样本少 | 早期用户基数小，反馈量天然低；但早期反馈密度最高、修复成本最低，此时建采集的成本也最低 |
| 用户误当工单系统 | 提交页明确「不承诺响应时效」；对外状态只给三态，不做时间承诺 |
| 正文含 PII（简历片段） | 不自动附带、不写台账、不入日志；单条删除 + 并入 R6 全量删除 |
| 被滥用为免费存储 | 限流 10 条/小时 + 内容去重 + 长度上限 |
| 与经历记忆库混淆 | 两者定位不同：反馈是**产品改进输入**，经历库是**简历内容输入**；共用交互壳与限流机制，但不合并为同一模块 |

## 九、待评审确认的问题

1. **回执通知**：后端无邮件通道，M1 仅靠站内列表可见。是否接受？若需邮件，应作为独立小项（接入 SMTP 配置）另行排期。
2. **对外状态粒度**：采用三态映射（已收到 / 处理中 / 已关闭），还是直接暴露五态？本方案倾向三态。
3. **限流阈值**：10 条/小时是否合适？是否需要为「bug」类放宽、为「feature」类收紧？
4. **是否允许未登录提交**：允许则降低门槛但引入匿名滥用与归属难题；本方案倾向**必须登录**，与现有鉴权一致。
5. **M1 入口位置**：账号下拉菜单（改动最小、不扩张主导航）+ 匹配失败与导出失败的错误横幅（命中现场）。是否同意该组合？
