# 经历记忆库（Experience Memory）设计方案 — 待评审

> 状态：**设计稿，待评审后实施**。对应 Plan.md「降级与观察项」中的登记项。
> 提出背景：用户希望后期增加 chat conversation，用记忆系统管理过往项目经历，作为简历优化依据。
> 本方案的核心主张：**对话是采集入口，结构化的经历库才是资产。**

---

## 一、问题与目标

### 1.1 问题
简历优化质量的瓶颈不在排版，而在**素材密度**：用户的项目背景、量化成果、技术决策理由散落在记忆与旧文档中，无法进入匹配链路。当前系统的输入只有「已有简历文本」，因此匹配再强也只能在有限素材上做排序与措辞。

### 1.2 目标
建立一个**用户可控、可检索、可复用**的经历素材库，使匹配与简历生成可以按 JD 定向取材：

1. 采集：把「写不出来」变成「答得出」——对话式追问降低录入门槛（M2）。
2. 沉淀：经历以结构化卡片存储，可检索、可复用、可迭代（M1 起）。
3. 消费：按 JD 检索相关经历，注入匹配与简历生成（M1 起）。
4. 缺口检测：主动指出时间线空白与缺失量化，形成改进清单（M3）。

### 1.3 非目标（Out of scope）
- 不做通用聊天助手（与产品无关的闲聊会稀释认知并消耗成本）。
- 不做多用户共享/团队素材库。
- M1 阶段不引入向量检索与 embedding。

---

## 二、核心设计决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 形态 | 经历记忆库（独立资源）+ 采集对话（入口） | 只做对话会产生不可检索的记录堆积，且每次匹配重复提问；沉淀才有复利 |
| 独立性 | 照 `cover_letters` 的解耦先例，做独立表与独立 CRUD | 经历不等同于简历：同一段经历可出现在多份简历中，且生命周期更长 |
| 入库门槛 | **候选卡片必须经用户确认**才落库为正式经历 | 简历会真实投递，模型补全的量化数据（虚报业绩）后果严重 |
| 检索 | M1 标签/技能过滤 + LLM 在候选集内选卡；M3 再评估 FTS5 | 单用户量级数十至数百条，向量库属过早优化，且引入运维成本 |
| 采集体验 | 缺口驱动的**点式追问**，而非访谈式长对话 | 长对话完成率低；一次只问一句、能立刻看到收益才可持续 |
| 计费 | 对话与抽取作为新的业务端点，计入 `credits` 与 `llm_usage` | 复用 R1 台账与既有扣费框架，不新增机制 |
| 隐私 | 不向台账写正文；对话与经历支持单条/全量删除与导出 | 经历数据的敏感度高于简历文本本身；沿用 R1 的「只记元数据」原则 |

## 三、数据模型（拟）

### 3.1 `experiences`（经历卡，M1）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | String(32) PK | |
| `user_id` | String(32) index | 归属用户 |
| `title` | String(255) | 项目/经历名称 |
| `org` | String(255) | 公司或组织 |
| `role` | String(128) | 角色/职位 |
| `start_date` / `end_date` | String(7) | `YYYY-MM`；`end_date` 空表示至今 |
| `context` | Text | 背景与目标（为什么做） |
| `actions` | Text | 做了什么（markdown，允许多条） |
| `outcomes` | Text | 结果，**鼓励量化**（如「延迟下降 40%」） |
| `skills` | Text(JSON) | 技能/技术栈数组，用于检索 |
| `tags` | Text(JSON) | 自由标签（行业、领域） |
| `status` | String(16) | `confirmed` / `archived`（M2 起增加 `draft`） |
| `source` | String(16) | `manual` / `conversation`（来源审计） |
| `source_message_id` | String(32) nullable | 对话来源消息，便于回溯与连带删除 |
| `created_at` / `updated_at` | DateTime | |

索引：`(user_id, status)`、`(user_id, start_date)`。

### 3.2 `conversations` / `conversation_messages`（对话，M2）

| 表 | 关键列 |
| --- | --- |
| `conversations` | `id` / `user_id` / `title` / `created_at` / `updated_at` |
| `conversation_messages` | `id` / `conversation_id`(FK, CASCADE) / `role`(`user`/`assistant`) / `content` / `created_at` |

删除对话时级联删除消息；由对话抽取出的经历卡保留（`source_message_id` 置空），因为经历是用户资产、对话只是过程。

### 3.3 与简历的关系（M1 不做表关联）

M1 采用**引用而非绑定**：匹配/生成请求显式传入选中的 `experience_ids`，不建多对多表。理由：绑定关系会随简历版本变化而失真，而显式传参更易推理、易回退。若 M3 出现「经历更新后自动同步到多份简历」的需求，再引入 `resume_experience_refs`。

## 四、接口契约（拟）

沿用现有约定：前缀 `/api`，JSON 字段 camelCase，DB 字段 snake_case；消耗积分的接口返回 `remainingCredits`。

### 4.1 M1 —— 经历卡 CRUD 与消费

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/experiences` | 列表（按 `status` / `tag` / 时间过滤） |
| `POST` | `/api/experiences` | 新建经历卡 |
| `GET` / `PUT` / `DELETE` | `/api/experiences/{id}` | 详情 / 更新 / 删除（归属校验，非本人 404） |
| `POST` | `/api/experiences/render` | 按 `ids` + 可选 JD 生成简历片段 markdown（**消耗积分**） |

匹配接口扩展（向后兼容，字段可选）：

```jsonc
// POST /api/derived-resumes
{
  "resumeText": "...",
  "jdText": "...",
  "experienceIds": ["exp_1", "exp_2"]   // 新增：为空的语义与现状完全一致
}
```

### 4.2 M2 —— 对话采集与确认式入库

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/conversations` | 新建会话（可传目标 JD 作为追问上下文） |
| `POST` | `/api/conversations/{id}/messages` | 发送消息，SSE 流式返回（复用 `/api/ai/polish` 的流式范式，**消耗积分**） |
| `POST` | `/api/conversations/{id}/extract` | 从会话抽取候选经历卡（**返回草稿，不落库**，消耗积分） |
| `POST` | `/api/experiences/from-draft` | 用户编辑确认后落库（不消耗积分） |

关键约束：`extract` 返回的草稿必须携带 `unverified: true` 标记字段（如模型推测的量化数据），前端高亮要求用户确认或删除。

### 4.3 M3 —— 检索与缺口检测

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/experiences/suggest?jd=...` | 按 JD 返回候选经历卡（标签过滤 + LLM 排序） |
| `GET` | `/api/experiences/gaps` | 时间线缺口 + 缺失量化项清单 |

## 五、检索与注入策略

M1 的注入流程（控制 prompt 体积是硬约束）：

1. **候选筛选（规则层）**：按 `skills`/`tags` 与 JD 关键词求交集，`status=confirmed`，时间倒序，**上限 30 条**。
2. **精排（LLM 层）**：不足 30 条时直接全给；超出时交由 LLM 在候选集内选 top-N（N ≤ 8）。
3. **注入格式**：经历卡序列化为紧凑 markdown（`### 项目 | 角色 | 时间` + 要点），附加约束「仅可使用给定事实，不得新增或放大数字」。
4. **可观测**：请求与响应记录到 `llm_usage`（沿用 R1，不记正文），便于评估注入带来的成本增量。

M3 再加 FTS5（contentless 虚表 + 触发器同步）作为关键词召回通道；只有当单用户经历数超过约 500 条、或标签过滤召回率明显不足时，才评估向量检索。

## 六、成本、配额与隐私

| 项 | 方案 |
| --- | --- |
| 计费端点 | 新增 `ENDPOINT_EXPERIENCE_CHAT`、`ENDPOINT_EXPERIENCE_EXTRACT`、`ENDPOINT_EXPERIENCE_RENDER` |
| 单价（待定） | 对话轮 1 credit、抽取 1 credit、渲染 1 credit（与 `cover_letter_cost` 同量级）；CRUD 不计费 |
| 限流 | 依赖 R2 落地后统一接入（对话类接口最需要按次限流） |
| 台账 | 沿用 R1：只记 `user_id / endpoint / model / token / 耗时 / 状态`，**不记对话正文** |
| 隐私 | ① 单条经历卡删除；② 对话级联删除；③ 全量导出/删除依赖 R6 的个人数据接口 |
| 数据最小化 | 对话上下文只在会话内使用，不默认注入匹配；仅用户选中的经历卡进入 prompt |

## 七、分期与验收

| 阶段 | 范围 | 验收标准 |
| --- | --- | --- |
| **M1** | 经历卡 CRUD + 匹配/生成时按 JD 选卡注入 | ① 可完整增删改查经历卡并在匹配时注入；② **假设验证**：同一简历与 JD，注入 vs 不注入的得分/人工评分对照（建议 ≥ 20 组样本，得分中位数提升或无显著下降）；③ 旧请求体（无 `experienceIds`）行为不变 |
| **M2** | 对话采集 + 抽取 + 确认入库 | ① 单轮对话可流式返回；② 抽取草稿可编辑确认后入库；③ 未确认的推测数据不会进入正式卡 |
| **M3** | 检索增强 + 缺口检测 + 经历渲染 | ① 按 JD 返回相关经历（召回人工抽查可用）；② 缺口清单可操作；③ 经历可生成简历模块 |

**M1 是整条路线的可证伪实验**：若注入经历并未提升匹配质量，则 M2/M3 不应继续投入。这是本方案最重要的一条约束。

## 八、依赖与风险

### 8.1 前置依赖

| 依赖 | 原因 |
| --- | --- |
| R1 LLM 用量台账 | ✅ 已就绪；对话与抽取的计费与成本观测直接复用 |
| R2 AI 限流与计费 | 对话类接口是无限流时最容易被滥用的端点 |
| R6 数据导出/删除 | 经历数据敏感度更高，删除通道必须在采集功能之前具备 |
| R4 匹配任务化 | 注入经历会加长匹配输入，先解决同步超时与失败兜底 |

### 8.2 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 采集完成率低（问答式投入重） | 缺口驱动的点式追问；每轮立即产出可见的经历卡 |
| 模型幻觉写入假业绩 | 草稿必确认；prompt 明确禁止新增/放大数字；`unverified` 标记高亮 |
| 成本失控 | 计费 + 按次限流（R2）；候选集上限 30 / 注入上限 8 |
| prompt 膨胀拖慢匹配 | 注入体积上限（建议 ≤ 4K token）；超限时以 LLM 精排压缩 |
| 隐私与合规 | 最小化注入、可删除、可导出；台账不记正文 |
| 与简历双写冲突 | 经历库为素材源，简历为发布物；单向「经历 → 简历」，不反向覆盖 |

## 九、待评审确认的问题

1. **单价与配额**：对话轮 1 credit 是否合理？是否需要针对对话单独设日限额？
2. **经历与简历的一致性**：是否需要反向同步（简历被手工编辑后回写经历库）？本方案倾向**不做**，避免双写冲突。
3. **M1 的验证指标**：以「匹配得分中位数」还是「用户主观评分」为准？前者易采集，后者更接近真实价值。
4. **对话入口位置**：独立页面，还是嵌在简历编辑器的时间线缺口处？本方案倾向后者（更贴合点式追问）。
