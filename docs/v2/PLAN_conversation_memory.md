## 0. 定性：从 Workflow 到 Agent MVP

### 0.1 一句话定性

**1.x 是「workflow 工具」**：用户手动触发一个个确定性流程（点「生成话术」→ 出话术；点「匹配」→ 出结果），系统是「被动的函数集合」。

**2.0 是「Agent MVP」**：用户给出**目标**（如「帮我投这个岗位」），Agent **自主理解目标、自主决定调用哪些工具、按需多步执行、中间可观察可纠正**，系统是「主动的代理」。

| 维度 | 1.x（workflow） | 2.0（Agent MVP） |
|---|---|---|
| 用户输入 | 具体操作（「生成打招呼话术」「匹配简历」） | **目标**（「帮我投这个岗位」「帮我准备面试」） |
| 系统行为 | 单次确定性流程 | **多步自主调度**（选简历→匹配→话术→优化，自动编排） |
| 决策权 | 完全在用户（一步步点） | **Agent 自主决策工具调用**，用户只需确认关键结果 |
| 交互 | 表单 + 按钮 | 对话 + 目标 + Agent 执行轨迹 |
| 核心资产 | 一套 LLM 函数 | 一个**能编排多个工具的 Agent 循环** |

### 0.2 Agent 自主度（已确认）

1. **目标驱动 + 工具自主选择**：Agent 根据目标自主决定调用哪些工具、按需多步。
2. **有限步骤的 ReAct**：推理→行动→观察→再推理的循环，但**限定最大步数（默认 5 步）**，超限停止并汇报，防止失控。

### 0.3 MVP 边界（什么「还不是」）

Agent MVP ≠ 通用 Agent。以下明确**不在 MVP 范围**：

| 不做 | 理由 |
|---|---|
| 开放自由聊天 | 目标是「求职任务」域，不是通用助理；chitchat 仅礼貌兜底引导回任务 |
| 无限步 ReAct | 限定 5 步，避免工具循环、成本失控、积分不可预判 |
| 隐式偏好学习 | 偏好仍是显式、可管理；自主决策 ≠ 静默学习 |
| 自动执行外部动作（发邮件、投递） | 只「生成可投递的产物」，不替用户对外提交 |

### 0.4 核心原则：自主但可观察、可纠正

Agent 的自主性**绝不等于黑盒**。三条铁律：

1. **每个工具调用可见**：Agent 的「思考 → 调了什么工具 → 结果」以执行轨迹形式呈现给用户。
2. **关键结果需确认**：自动选简历、生成话术等结果，用户可一键纠正（「换份简历」「换语气」）。
3. **积分可预判**：计费口径统一为「**工具 0 积分、生成动作按现有单价计费**（话术 1 / 匹配 5）」；`select_resume` 的比较式打分调用不扣积分，但计入 `llm_usage` 观测成本。用户在发起前能看到「预计最多消耗 N 积分」（N = 本次生成动作单价；因每次生成后本轮即结束，单轮最多一次生成）。

## 1. 现状诊断（已核实代码）

### 1.1 当前是「无状态 workflow」——2.0 要升级为 Agent

| 环节 | 现状 | 缺口 | 2.0 Agent 改造 |
|---|---|---|---|
| 简历选择 | 前端让用户手动挑一份简历，把 `resumeText` 传给后端 | 后端无「从简历库自动选」能力 | Agent 自主选简历（可纠正） |
| 话术生成 | `POST /api/cover-letters` 单次调用，输入 `resume_text + jd_text + scene` | 无偏好、无上下文、无对话 | 收敛为 Agent 工具 `generate_cover_letter` |
| 简历匹配 | `POST /api/derived-resumes` 单次调用，`run_match` 无状态图 | 无偏好、无上下文 | 收敛为 Agent 工具 `match_resume` |
| 编排 | 无——用户手动按序点击 | 无「多步自主编排」能力 | ReAct 循环自主编排多工具 |
| 记忆 | 无任何偏好存储 | 用户每次重新选简历/描述语气 | 三态记忆系统（§2C） |

### 1.2 关键事实

- `MasterResume` 支持**一个用户多份简历**（`user_id` + 标题唯一），自动选简历的**数据前提已具备**。
- `CoverLetter.scene` 已有 `greeting / followup / interview` 三场景，但语气、称呼、长度偏好无存储。
- 后端 LLM 调用统一经 `app/core/llm.py`（`model` / `get_match_llm`），意图识别与自动选简历可复用同一客户端。

## 2. 数据模型设计（三大设计维度的数据基础）

> 本节是 §2A/2B/2C（上下文/工具/记忆）共用的数据底座。两张表中：`user_preferences` 承载长期记忆，`conversation_messages` 承载工作记忆 + 情景记忆。（原第三张 `resume_match_scores` 缓存表经 MVP 复审移除，见 §2.1.2。）

### 2.1 新增两张表（全部 append-friendly）

#### 2.1.1 `user_preferences`（用户偏好，单例/少量行）

| 列 | 类型 | 说明 |
|---|---|---|
| id | String(32) PK | uuid |
| user_id | String(32) | 归属用户，唯一索引 |
| default_resume_id | String(32) \| NULL | 默认简历（自动选简历的兜底） |
| tone | String(16) | 默认语气：formal / friendly / concise |
| salutation | String(64) | 默认称呼（如「您好」「XX 老师」） |
| max_length | Integer \| NULL | 话术长度偏好（字数上限，可空） |
| created_at / updated_at | DateTime | 时间戳 |

> 设计原则：偏好是**显式、可管理**的。全部字段可由用户在「偏好设置」页查看/修改/清空。不做隐式推断（P2）。

#### 2.1.2 ~~`resume_match_scores`（简历↔岗位匹配分缓存）~~ —— MVP 移除，不建此表

> **MVP 复审结论：不建此表。** 自动选简历改为**单次比较式调用**（一次 LLM 调用输入全部简历摘要，输出选择 + 理由，见 §2B.5），无逐简历打分，缓存失去存在前提；且 JD 文本通常每次唯一，指纹缓存命中率天然偏低。若上线后 `llm_usage` 数据显示选简历成本显著，再评估引入缓存。

#### 2.1.2 `conversation_messages`（对话消息）

| 列 | 类型 | 说明 |
|---|---|---|
| id | String(32) PK | uuid |
| user_id | String(32) | 归属用户 |
| job_id | String(32) | 归属岗位（一会话=一岗位） |
| role | String(16) | user / assistant / system / tool |
| content | Text | 消息正文 |
| intent | String(16) \| NULL | 意图识别结果（cover_letter / match / followup / refine） |
| payload | Text \| NULL | 结构化附件（如匹配结果快照 JSON） |
| created_at | DateTime | 时间 |

> 这是「对话式交互」的落点。一会话 = 一岗位（`job_id`），消息按 `created_at` 升序构成对话流。

### 2.2 关系

- `user_preferences` 1↔1 user
- `conversation_messages` N→1 job（**删除岗位级联清空会话消息**；反向不成立——删除会话仅清消息，岗位卡与其匹配/话术资产不动，见 §4）
- ~~`resume_match_scores`~~ 已移除（MVP 复审），见 §2.1.2

## 2A. 上下文设计（Context）

### 2A.1 设计目标

对话式入口的核心是**每轮 LLM 调用都拿到「恰好够用、不冗余」的上下文**。上下文过少则丢失连贯性（不知道上一轮在聊哪个岗位、选了什么简历）；过多则 token 膨胀、成本线性增长、且无关信息会稀释模型注意力。

**原则**：上下文是**装配出来的**（每轮按需组装），不是「把整个对话历史原样塞进去」。去掉无关属性，只保留影响本轮决策与生成的字段。

### 2A.2 上下文分层（三层）

| 层 | 内容 | 生命周期 | 载体 |
|---|---|---|---|
| **L1 会话上下文** | 当前会话的近期消息（用户 + AI），含岗位、简历、意图 | 单会话内 | `conversation_messages` 最近 N 轮 |
| **L2 任务上下文** | 当前岗位 JD 快照 + 选定简历文本 + 上一条生成结果 | 单次任务 | 会话内引用 + `payload` 快照 |
| **L3 用户上下文** | 显式偏好（默认简历/语气/称呼/长度） | 跨会话长期 | `user_preferences` |

### 2A.3 上下文装配（每轮 `build_context()`）

```
build_context(user_id, job_id, current_message) →
  L3 偏好       ← user_preferences（1 行，字段级）
  L1 近期消息   ← conversation_messages 最近 N=6 轮（去 payload 大字段）
  L2 任务快照   ← job.jd_text 摘要 + 选定简历标题 + 上一条 assistant 结果引用
```

**关键：去掉无关属性**。装配时显式剔除以下字段，只保留精简视图：

| 剔除项 | 理由 |
|---|---|
| `payload` 大字段（匹配结果完整 JSON、简历全文） | 历史消息仅保留 `content` 摘要 + `message_id` 引用，需要全文时再按 id 拉取 |
| 系统消息（`role=system` 的 prompt 原文） | 每次重放是浪费 token，系统 prompt 在生成侧固定注入 |
| 过期轮次（超出 N=6 轮） | 超出窗口的消息不进上下文，仅保留「早前摘要」一句（见 §4 情景记忆） |
| 重复的 JD/简历全文 | L2 任务快照只放一次，不放进每轮 L1 消息 |

### 2A.4 上下文结构（传给 LLM 的实际形态）

```json
{
  "user": { "tone": "formal", "salutation": "您好", "max_length": 150 },
  "job": { "id": "...", "title": "前端工程师", "jd_summary": "Vue/TS/工程化（150字内）" },
  "resume": { "id": "...", "title": "前端简历", "selected_by": "auto" },
  "history": [ {"role": "user", "content": "写打招呼话术"}, {"role": "assistant", "content": "（上一条话术摘要）"} ],
  "current": { "intent": "cover_letter", "scene": "greeting" }
}
```

> **边界**：`jd_summary` 是 JD 原文的**摘要**（150 字内），不是全文。JD 全文只在「首次建档 + 首次匹配」时进入 LLM（走 `run_match` / `run_cover_letter` 的 `jd_text` 参数），后续轮次的上下文只带摘要。这避免同一份 JD 在多轮对话里被反复塞入完整文本。

## 2B. 工具设计（Tools）

### 2B.1 设计原则：工具 ≠ LLM 生成

**核心原则**：工具是 Agent 用来**感知环境、获取事实、执行动作**的**确定性能力**，不是 LLM 生成动作本身。

上一版把「生成话术」「匹配简历」当作工具，是方向性错误——那些本质是** LLM 调用**（`run_cover_letter` / `run_match` 内部就是 `model.ainvoke`），是 Agent 的**最终产出**，不是「工具」。

正确的关系是：

```
┌─ 工具（确定性、非 LLM）：Agent 用它搞清楚状况、准备素材、更新状态
│    感知类：读岗位、读简历库、查积分、查重
│    操作类：建岗位、确认投递、更新偏好、导出 PDF
│
└─ 生成（LLM）：Agent 决策之后的「产出」，不是工具
     话术生成、简历匹配/优化、简历改写 —— 这些是 Agent 要交付的结果
```

**为什么必须这样划分**：

1. **工具要「可靠、可预期」**：工具是 Agent 的「手和眼」，必须确定性执行、返回精确事实。如果工具本身就是 LLM 调用，Agent 就在「用另一个 LLM 去感知环境」，结果不可控、不可审计。
2. **生成是「一次性产出」而非「可组合步骤」**：话术/匹配是 Agent 任务的终点，不是中间步骤。把它们当工具，会让 Agent 在 ReAct 里「反复调 LLM 生成」，成本爆炸且无意义。
3. **Function Calling 的语义**：LLM 选工具是为了「获取它不知道的信息」或「触发副作用」。LLM 生成动作不需要「选」——它就是 LLM 本身要做的事。

### 2B.2 工具清单（确定性能力，复用现有 API/服务）

| 类别 | 工具 | 输入 | 输出 | 对应现有能力 | 计费 |
|---|---|---|---|---|---|
| **感知** | `get_job` | `job_id` | 岗位详情（JD/状态/已有话术/匹配） | `GET /api/jobs/{id}` | 0 |
| **感知** | `list_resumes` | — | 用户简历库（id + 标题） | `GET /api/resumes` | 0 |
| **感知** | `get_quota` | — | 剩余积分 | 现有 quota 服务 | 0 |
| **感知** | `detect_job` | `jd_text` | 是否已有相同岗位（job_id / null） | `POST /api/jobs/detect` | 0 |
| **操作** | `create_job` | `jd_text`, `title?`, `company?` | 新建岗位卡 | `POST /api/jobs` | 0 |
| **操作** | `mark_applied` / `mark_closed` | `job_id` | 确认投递成功 / 归档（**必须经既有 mark 端点 → `services/job.py::transition()`**，不得绕过 operation-driven 状态机直写 `job.status`） | `POST /api/jobs/{id}/mark` | 0 |
| **操作** | `update_preferences` | 偏好字段 | 更新长期记忆 | 新增 preferences 服务 | 0 |
| **操作** | `export_pdf` | `resume_id` | 导出简历 PDF | 现有 pdf_export 服务 | 0 |

> **注意**：`select_resume`（自动选简历）**不是独立的工具**——它是「生成」链路的前置决策，内部需要 LLM 打分（语义匹配）。它不属于「确定性工具」，而是**生成动作的参数解析**（见 §2B.5）。

### 2B.3 工具的三层结构（生产可用的关键）

每个工具是**确定性函数**，三层结构：

```
┌─ Schema 层：Pydantic 输入/输出模型（Function Calling 的 tool schema）
├─ 执行层：复用现有 API/服务逻辑（get_job → 读 Job 表；create_job → attach_or_create_job）
└─ 观测层：挂 span / 审计 / 越权校验（复用 trace_observability + get_current_user）
```

**关键：工具 100% 复用现有确定性逻辑，零新增 LLM 调用。** 工具执行层就是现有 `app/api/*` 和 `app/services/*` 里的确定性函数，只是把它们从「HTTP 端点」暴露为「Agent 可调用的函数」。

### 2B.4 生成动作（LLM 产出，不是工具）

Agent 的「生成」动作**不注册为 Function Calling 工具**，而是由 ReAct 循环在特定条件下触发：

| 生成动作 | 触发条件 | 本质 | 计费 |
|---|---|---|---|
| 生成话术 | Agent 判断「需要话术」 | `run_cover_letter_stream`（LLM 流式） | 1 积分 |
| 简历匹配/优化 | Agent 判断「需要匹配」 | `run_match`（LLM） | 5 积分 |
| 简历改写/迭代 | 用户要求 refine | 复用 rewrite 链路 | 按场景 |

**如何区分「工具调用」与「生成动作」**：Agent 的 ReAct 循环里，**工具调用 = 确定性函数**（读/写/查），**生成动作 = Agent 输出最终内容**。生成动作是循环的「终点」（产出后本轮结束），工具调用是循环的「中间步骤」（产出后继续推理）。

### 2B.5 自动选简历：生成动作的参数解析（非独立工具）

`select_resume` 不是确定性工具（它要 LLM 算语义匹配分），但也不是完整的「生成产出」。它属于**生成动作的参数解析**：

```
Agent 决定「要生成话术/匹配」
  → 但缺参数：用哪份简历？
  → 参数解析：单次比较式调用（全部简历摘要一次输入，输出选择+理由）
  → 结果「已选《前端简历》」作为**推荐**呈现，用户可纠正
  → 用选定简历执行生成动作
```

**为什么它是「参数解析」而非「工具」**：因为它的输出（选哪份简历）不直接呈现给用户，而是喂给下一个生成动作作为参数。它本质是「生成动作的前置决策」，与「读岗位」「建岗位」这类「返回事实/触发副作用」的工具性质不同。

### 2B.6 工具与生成动作的完整协作（一次目标执行）

```
用户目标「帮我投这个岗位」
  第 1 步 [工具] list_resumes()        → 3 份简历（确定性读库）
  第 2 步 [参数解析] 选简历            → 「前端简历」（LLM 打分，可纠正）
  第 3 步 [工具] get_job(job_id)       → JD 全文 + 状态（确定性读库）
  第 4 步 [生成] 匹配简历              → 匹配度 82%（LLM 产出，本轮终点）
  —— 用户确认匹配结果 ——
  第 5 步 [生成] 生成打招呼话术        → 话术（LLM 产出）
  第 6 步 [工具] mark_applied(job_id)  → 状态推进到已投递（确定性写库）
```

## 2C. 记忆设计（Memory）

### 2C.1 最小可用记忆系统（三态）

记忆系统的目标：**让系统在不同时间尺度上「记住该记住的、忘掉该忘掉的」**。采用经典的三态划分，但每态都按「最小可用」裁剪，不做过度设计。

| 记忆态 | 定义 | 时间尺度 | 存储 | 容量上限 | 生命周期 |
|---|---|---|---|---|---|
| **工作记忆（Working）** | 当前对话的即时上下文 | 秒~分钟 | `conversation_messages` 最近 N 轮 | N=6 轮 | 会话内 |
| **情景记忆（Episodic）** | 某个岗位会话的完整过程 | 分钟~天 | `conversation_messages` 全量（按 job_id） | 按岗位聚合 | 随岗位删除级联清除 |
| **长期记忆（Semantic/Long-term）** | 跨会话的用户稳定偏好 | 周~永久 | `user_preferences` | 单行（用户级） | 用户显式管理 |

### 2C.2 工作记忆（Working Memory）

- **内容**：当前会话最近 N=6 轮消息（用户 + AI 摘要）。
- **实现**：`build_context()` 从 `conversation_messages` 取最近 6 条，剔除 `payload` 大字段，仅保留 `content` + `intent`。
- **作用**：让「refine」「追问」能引用上一轮，而不需要重放整个会话。
- **为何是「消息列表」而非「压缩摘要」**：工作记忆要求**低延迟、精确**。6 轮原文（去大字段）token 成本可控（约 2-3K token），无需做摘要压缩。超过 6 轮的部分才进入情景记忆压缩。

### 2C.3 情景记忆（Episodic Memory）

- **内容**：一个岗位会话的**完整过程**——用户提了什么、AI 生成了什么、选了哪份简历、最终接受哪份结果。
- **实现**：`conversation_messages` 全量按 `job_id` 聚合，天然是情景记忆的存储。不额外建表。
- **作用**：用户重新打开某个岗位会话时，能完整回看历史（这是「对话历史」菜单项的数据源）。
- **关键**：情景记忆是**显式的、可见的、可删除的**（删除岗位级联清除该岗位全部会话消息；**删除会话仅清消息，不影响岗位卡及其匹配/话术资产**，二者删除语义已解耦，见 §4）。不做「自动遗忘」——用户明确主导情景记忆的生命周期。

### 2C.4 长期记忆（Long-term / Semantic Memory）

- **内容**：跨会话稳定的用户偏好——默认简历、语气、称呼、长度。这是**语义化**的（提炼出的稳定属性），而非原始行为记录。
- **实现**：`user_preferences` 表，用户级单行。**仅显式存储**，不从行为隐式推断（P2 明确不做）。
- **作用**：自动选简历的兜底、话术生成的语气/称呼/长度默认值。
- **为何不存「投递习惯」**：投递时间规律、岗位类型分布属于 P1（行为统计洞察），不是「用户可管理的偏好」，且需要大量数据冷启动。长期记忆只存「用户明确设置、可一键修改」的稳定属性。

### 2C.5 三种记忆的协同（一次完整交互）

```
用户打开「字节跳动·前端工程师」会话
  → 情景记忆加载：全量历史消息（该 job_id）
  → 长期记忆加载：user_preferences（默认简历/语气/称呼）
  → 用户输入「帮我写打招呼话术」
  → 工作记忆装配：最近 6 轮 + 偏好 + 任务快照 → build_context()
  → ReAct：Agent 判断需生成话术 → 解析简历 → 生成话术（注入偏好）
  → 结果写入：conversation_messages（更新情景记忆）
  → 若用户设置「默认语气=正式」，写 user_preferences（更新长期记忆）
```

### 2C.6 记忆边界（最小可用 vs 过度设计）

| 明确做（最小可用） | 明确不做（本阶段） |
|---|---|
| 工作记忆 = 最近 6 轮去重消息 | ❌ 工作记忆的 LLM 动态压缩/总结 |
| 情景记忆 = 岗位会话全量消息 | ❌ 情景记忆的自动摘要/遗忘曲线 |
| 长期记忆 = 显式偏好单行 | ❌ 从行为隐式推断长期记忆（P2） |
| 三种记忆都可见、可管理 | ❌ 向量化语义检索记忆（无必要，偏好是字段级） |

## 3. ReAct 循环（Agent 的执行引擎）

### 3.1 循环结构（有限步骤）

Agent MVP 的核心是 **ReAct 循环**：推理（Reason）→ 行动（Act）→ 观察（Observe）→ 再推理，直到达成目标或达到步骤上限。

```
loop（最多 max_steps = 5 步）:
  1. Reason  ：LLM 基于当前上下文 + 观察历史，决定「下一步做什么」
  2. Act     ：调用确定性工具（Function Calling），或触发生成动作，或输出最终回答
  3. Observe ：执行工具/生成，得到结果，作为 tool/assistant 消息回填
  4. 判断     ：若 LLM 输出「最终回答」或步数达到 5，退出循环
```

**关键约束：有限步骤。** `max_steps = 5`，超限强制停止，把已完成的中间结果汇报给用户，并询问是否继续。这防止工具循环、成本失控、积分不可预判。

### 3.2 一次典型执行（目标「帮我投这个岗位」）

| 步 | 阶段 | 动作 | 结果 |
|---|---|---|---|
| 0 | 输入 | 用户：「帮我投这个岗位」 | — |
| 1 | Reason+Act | 思考「需要先确定简历」，调用**工具** `list_resumes()` | 3 份简历（确定性读库） |
| 2 | 参数解析 | 选简历（LLM 打分，可纠正） | 「前端简历」 |
| 3 | Reason+Act | 思考「做匹配」，触发**生成动作** `run_match` | 匹配度 82%（LLM 产出） |
| 4 | Reason | 思考「匹配完成，问是否继续出话术」，输出汇报 | 「已选前端简历，匹配 82%」 |

> 注：生成动作（匹配、话术）是 ReAct 的**产出终点**，每次生成后本轮循环结束，等用户确认再进下一轮——避免 Agent 在一步内连续多次调用 LLM 生成（成本不可控）。

### 3.3 与「意图识别」的关系（重要澄清）

Agent MVP **不再需要独立的意图识别层**。原「intent_router → 封闭枚举」是 workflow 思路——把用户输入分类成固定动作。在 Agent 范式下：

- **意图判断由 ReAct 的 Reason 步骤完成**：LLM 在第一步推理时，自然会「理解目标 → 决定调用哪个工具/触发哪个生成」，这本身就是意图识别，且比固定枚举更灵活。
- **chitchat 兜底仍保留**：若用户输入是闲聊（「你好」「今天天气」），LLM 判断「无需调用工具/生成」，直接输出礼貌回复引导回任务。这是 Reason 的自然结果，不需要单独的 intent 模型。

**保留一个轻量约束**：系统 prompt 里声明「你是一个求职 Agent，只处理简历匹配与话术生成相关目标；与求职无关的闲聊请礼貌引导回任务」。这是**行为约束**（写在 system prompt），而非**独立的意图分类器**。

### 3.4 自动选简历（生成动作的参数解析）

自动选简历是**生成动作的前置参数解析**，不是独立工具（详见 §2B.5）：

- Agent 判断「要生成话术/匹配」但缺「用哪份简历」时，触发参数解析。
- 解析逻辑（MVP 复审修订）：**单次比较式调用**——一次 LLM 调用输入全部候选简历的标题 + 摘要（各 ≤150 字），输出「选中简历 + 选择理由」，N 次逐简历打分收敛为 1 次；`default_resume_id` 作为平分/异常兜底 → 返回推荐。
- **可纠正**：Agent 把「已选《前端简历》」作为轨迹呈现，用户可回复「换成后端简历」，Agent 用指定简历重做。

### 3.5 偏好记忆的应用点（在 Agent 中）

| 偏好字段 | Agent 中的应用 | 注入方式 |
|---|---|---|
| default_resume_id | 选简历的兜底 | 参数解析层直接读取 |
| tone | 话术生成的默认语气 | 生成动作执行时注入 prompt |
| salutation | 话术 prompt | 注入称呼 |
| max_length | 话术 prompt | 注入长度约束 |

> 偏好在**生成动作执行层**注入（而非 ReAct 的 prompt 里塞给 LLM 决策），保证偏好是「确定性约束」，不因 LLM 的自主推理而漂移。

## 4. P0 API 设计

| 端点 | 变更 |
|---|---|
| `POST /api/conversations/{job_id}/message` | 新增：发送一条对话消息，内部走 **ReAct 循环（Reason→Act→Observe，最多 5 步）**，**响应为 `text/event-stream`（SSE 流式）** |
| `GET /api/conversations/{job_id}` | 新增：拉取该岗位的完整对话消息流 |
| `GET /api/preferences` / `PUT /api/preferences` | 新增：读取/更新显式偏好 |
| `POST /api/resumes/select` | 新增：给定 JD，单次比较式调用返回自动选中的简历 + 选择理由（供「切换」） |
| `DELETE /api/conversations/{job_id}` | 删除会话：**仅删除该岗位的 `conversation_messages`**；岗位卡、匹配、话术等资产不动（删除岗位走既有岗位 purge 入口，届时级联清消息） |

> **入口改造**：2.0 不再保留非对话式入口。现有 `POST /api/cover-letters`、`POST /api/derived-resumes` 两个单次端点**收敛为对话式端点的内部实现**——即「话术生成 / 简历匹配」不再是独立可调用的资源端点，而是 `POST /api/conversations/{job_id}/message` 的 ReAct 循环里 Agent 触发的**生成动作**（`run_cover_letter_stream` / `run_match`）。前端仅暴露对话式入口页。具体收敛策略见 §4.2。

### 4.1 SSE 流式输出（P0 必做）

**目标**：对话式消息生成走流式，逐 token 推送给前端，消除「点发送 → 长时间白屏等待」的体验断层。这是对话式产品（ChatGPT/Claude）的标准体验，用户已明确要求。

**技术落点**（已核实代码）：

| 环节 | 现状 | 流式改造 |
|---|---|---|
| 话术链路 `run_cover_letter` | `model.ainvoke(prompt)` 一次性返回 | 新增 `run_cover_letter_stream()`，用 `model.astream(prompt)` 逐 chunk 产出 |
| 匹配链路 `run_match` | LangGraph 图 `graph.ainvoke()`，内含结构化输出节点 | **不流式**（结构化 JSON 无法逐字流式，且流式会破坏 json_mode 解析） |
| 意图识别 | 单次 `ainvoke` | **不流式**（前置决策，输出极短） |

**关键设计决策：流式范围仅限「话术生成」，不含匹配与意图识别。**

理由有三：

1. **话术是自由文本**，天然适合流式（`astream` 逐 chunk 输出纯文本）。
2. **匹配产出的是结构化 JSON**（`MatchResult` / `MatchAnalysisBundle`，经 `with_structured_output` + `json_mode`），流式输出会打碎 JSON 解析，得不偿失。匹配的体验优化应靠「进度事件」（见下），而非逐字流式。
3. **意图识别是前置短输出**，流式无意义。

**SSE 事件协议**（`text/event-stream`）：

```
event: reasoning       data: {"text": "我需要先选简历，再做匹配"}   # ReAct 思考（可选，仅当模型支持推理内容）
event: tool_call       data: {"tool": "select_resume", "args": {...}}  # Agent 调用工具（轨迹可见）
event: tool_result     data: {"tool": "select_resume", "result": {...}} # 工具执行结果
event: resume_selected data: {"resume_id": "...", "title": "前端简历"}  # 自动选简历结果（可纠正提示）
event: message         data: {"delta": "您好，"}        # 话术逐 token 增量
event: done            data: {"message_id": "...", "content": "..."}   # 结束，附完整结果
event: error           data: {"message": "..."}           # 异常终止
```

**对匹配链路的进度反馈**（非流式场景的等价体验）：匹配虽不流式文本，但 LangGraph 各节点（`jd_extract` → `resume_match` → `keyword_optimize`）可在节点间推送 `event: stage` 进度事件（如「正在解析 JD…」「正在分析匹配度…」「正在优化简历…」），让用户感知推进而非白屏。

**工程要点**：

| 项 | 说明 |
|---|---|
| 后端 | 使用 `StreamingResponse` + `media_type="text/event-stream"`；生成器内部 `async for chunk in model.astream(...)`，chunk 内容经 `_to_text` 归一化后作为 `delta` 推送 |
| 超时/断连 | 客户端断开时停止生成（`asyncio.CancelledError` 处理），避免后端空转消耗 token |
| 计费 | **仍按「一次操作」扣固定积分**（工具 0 积分、生成动作按现有单价，见 §0.4），流式不改变计费单位，仅在生成前扣减，生成中断不退（与现有 regenerate 语义一致） |
| 落库 | 流式过程中不落库；`done` 事件触发时，把完整文本写入 `conversation_messages`（assistant 消息）与 `cover_letter` 记录，保证「流式展示」与「持久化」解耦。**断连兜底（MVP 复审补充）**：客户端在 `done` 前断连时，把已生成片段落库为 assistant 消息（标记 `interrupted`），避免「已扣积分 + 内容丢失」双重损失 |
| 前端 | 用 `fetch` + `ReadableStream` 消费 SSE（或 `EventSource`，但 `POST` 需用 fetch）；逐 `delta` 追加到当前 AI 气泡 |
| 兜底 | 若 LLM 厂商不支持流式（`astream` 退化为单 chunk），SSE 仍正常，只是「一次推完」，前端无需区分 |

### 4.2 入口改造策略（仅「简历匹配」菜单）

2.0 的入口改造**严格限定在「简历匹配」这一个菜单**：把当前 `match` 页（已同时承载「简历匹配 + 话术」两类平级任务）改造为对话式入口页。其余 3 个菜单（岗位卡、投递分析、我的简历）保持不动。

| 层 | 1.x 现状 | 2.0 改造 | 处置 |
|---|---|---|---|
| 菜单 | 4 项固定菜单，`match` 承载匹配+话术 | 仅 `match` 菜单改造为对话式入口页 | 其余 3 项不动 |
| 前端入口 | `match` 页用 TaskModePicker 平级选择「匹配/话术/两者」 | 改为对话式入口页，以对话形式发起匹配/话术 | 旧 TaskModePicker/表单抽屉移除 |
| 后端端点 | `POST /api/cover-letters`、`POST /api/derived-resumes` 独立可调用 | 收敛为 `POST /api/conversations/{job_id}/message` 内部调用的服务函数 | 旧端点移除（见下） |

**后端收敛的具体策略**：

1. **服务层复用**：`run_cover_letter` → 新增 `run_cover_letter_stream`；`run_match` 保持，二者作为 `conversation` 路由的内部服务，不再作为独立资源端点暴露。
2. **旧端点处置（MVP 复审修订）**：**仅移除两个 POST 生成路由**（`POST /api/cover-letters`、`POST /api/derived-resumes`）；两类资源下的 GET / PUT / DELETE、`{id}/accept`、`/observability`（统一观测页依赖，`lib/jobmatch.ts` 已核实）**全部保留**。且采用 **strangler 策略**：本迭代先下线前端入口（仅对话式入口可见），旧 POST 路由**保留一个迭代**作为回滚通道，待 §7.1 产品级验收数据支持后再移除路由并清理 TaskModePicker 死代码。前后端同仓同发、无外部 API 消费者，技术上可随时移除。
3. **数据兼容**：`cover_letters` / `derived_resumes` 两张表保留（作为对话消息 `payload` 的持久化载体），仅**入口**从独立端点改为对话端点。表结构可复用，无需迁移旧数据。
4. **前端改造**：`match` 页整体重构为对话式入口页；岗位卡页（`jobs`）详情里通过 `?job=<id>&mode=...` 跳转到 `match` 页恢复上下文的既有联动，需适配为跳转到新的对话式入口并带上下文。

## 5. 风险与权衡

| 风险 | 影响 | 缓解 |
|---|---|---|
| 自动选简历语义匹配成本 | 每个新 JD 一次比较式 LLM 调用（与简历数无关） | 单次比较式调用；成本经 `llm_usage` 观测，显著时再评估缓存 |
| 选错简历静默产出错误结果 | 用户信任崩塌 | 强制「已选简历」可见 + 一键切换，绝不静默 |
| **ReAct 失控 / 工具循环** | 无限调用工具、成本失控、积分不可预判 | `max_steps=5` 硬上限 + 工具白名单封闭 + 每步轨迹可见 |
| **Agent 幻觉调用工具 / 传错参数** | 走错链路、产出错误结果 | 工具内部确定性校验（参数 schema 强校验）；关键结果需用户确认 |
| 对话历史 token 膨胀 | 多轮对话成本线性增长 | 上下文窗口限制（最近 N 轮）；工具结果只保留摘要不保留全文 |
| 偏好存储隐私 | 用户偏好属个人数据 | 显式可管理、可清空；不存储敏感内容（JD 原文、简历全文不重复存） |
| 删除语义一致性 | 对话页删 vs 岗位卡页删不同源 | 收敛到同一后端删除端点 |

## 6. 明确不做（范围边界）

- ❌ 隐式偏好学习（P2）：从行为静默推断偏好并自动应用
- ❌ 开放自由聊天：Agent 限定在「求职任务域」，chitchat 仅礼貌兜底引导回任务（system prompt 行为约束）
- ❌ 投递习惯记忆（P1）：投递时间规律、岗位类型分布洞察
- ❌ 多简历「打分详情页」：只返回选中简历 + 简要理由，不做可视化对比
- ❌ 自动执行外部动作（发邮件/投递）：Agent 只「生成可投递产物」，不替用户对外提交
- ❌ 无限步 ReAct：限定 `max_steps=5`，不开放无限自主循环

> **注意**：SSE 流式输出**已由用户明确指定为 P0 必做**，故从「不做」清单中移除，详见新增 §4.1。

### 7.1 产品级验收指标（MVP 复审新增）

Agent MVP 的核心假设——「目标驱动的对话式编排优于逐步表单操作」——必须由数据裁决，不以「代码已写」代替「产品已验证」：

| 指标 | 目标 | 采集方式 |
|---|---|---|
| 一次目标完成率 | 对话入口 ≥ 旧表单入口 | 会话内生成动作成功落库率 |
| 平均步数 | 每次目标 ≤ 3 步（工具 + 生成合计） | ReAct 轨迹（tool 消息）统计 |
| 工具调用错误率 | < 5%（参数校验失败/越权/白名单外） | 工具观测层 span |
| 每目标积分消耗中位数 | ≤ 旧表单路径（1 或 5 积分） | credits 流水 |
| 漏斗对照 | 对话入口「发起 → 产出 → 确认」转化 ≥ 旧表单 | growth 事件（复用 `first_match_success` 等既有埋点） |

**回滚策略**：旧表单入口代码与两个 POST 生成路由保留一个迭代；若验收指标显著劣于旧路径，恢复前端入口开关即可回滚，无需代码回退。数据支持后（下一迭代）再移除旧路由与 TaskModePicker 死代码。

## 8. 评审清单

请确认以下 9 项：

1. **Agent 定性**：接受「2.0 = Agent MVP，用户给目标、Agent 自主多步调度工具」，而非「workflow + 对话式包装」？（**这是本次最根本的定性**）
2. **ReAct 有限步骤**：接受「有限 5 步 ReAct 循环，超限停止汇报」，而非无限自主循环？
3. **工具边界（§2B，本次修正核心）**：接受「工具 = 8 个确定性能力（读岗位/读简历/查积分/查重/建岗位/确认投递/更新偏好/导出 PDF），**LLM 生成（话术/匹配/改写）不是工具，而是 Agent 的最终产出**」？即彻底摒弃上一版「把 LLM 生成函数当工具」的错误设计。

6. **对话承载**：一会话 = 一岗位；删除岗位级联清空会话消息，**删除会话仅清消息、不影响岗位卡**（2026-11-09 MVP 复审修订，原「删除会话=级联删岗位」作废）？
